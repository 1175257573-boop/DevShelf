# DevShelf · 多项目代码资产治理 Agent

> 一个基于 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 的代码资产治理 Agent：
> 自动扫描本地代码仓库，解析技术栈与结构，评估项目健康度，持久化项目画像，
> 并把画像暴露为模型可调用的工具，让模型按需完成检索、盘点与报告产出。

**状态：设计完成，工程实现待启动。** 本 README 描述的是设计意图，不是已实现的功能。

---

## 解决什么问题

个人手里往往有十几个技术栈各异、状态不一的代码仓库。要回答这些问题，
通常靠记忆和手动翻找：

- 我有哪些项目用了 PyTorch？
- 哪些项目超过一个月没动过了？
- 某个功能当初是怎么排查出来的？

这套信息不落到机器可读的结构上，模型就只能靠猜。而模型一旦开始编造技术细节，
产出就不可信。

DevShelf 的做法是：**先把事实从代码和 git 历史里抽出来固化成项目画像，
再让模型基于画像做推理**。所有结论都必须带证据位置。

## 链路设计

六段链路，前三段是自有内核代码，后两段交给 dsh 编排，最后一段是产出：

| 段 | 职责 | 归属 |
|---|---|---|
| 1 采集 | git 历史、文件树、依赖清单 | 自有内核 |
| 2 解析 | tree-sitter 解析 AST，抽取技术栈标签 | 自有内核 |
| 3 评分 | 活跃度、文档完整度、测试存在性、风险标记 | 自有内核 |
| 4 记忆 | 项目画像持久化与增量合并 | 自有内核 |
| 5 编排 | 工具注册、流程指令、留痕 | **dsh 框架** |
| 6 产出 | 周报 / 技术栈盘点 / 简历素材 | 自有内核 |

### 一个刻意的架构决定

dsh 目前处于 developer preview，官方明确说明核心 API 会持续演进、存在破坏性变更。
如果把业务逻辑直接写进 dsh 插件，框架一次升级就要重写。

所以做了分层：**业务逻辑下沉到独立的 Python 服务，
dsh 插件层只做工具注册与参数转发，不含任何业务逻辑**。框架可替换，内核资产不受影响。

具体来说，画像存储不依赖框架的会话持久化能力，
而是自己管理 JSON 文件与增量合并——这既是解耦，也避开了框架侧的能力缺口。

## 评估设计

项目按「每个结论都要能被核对」的标准来做，而不是 demo 跑通即止。

- **标注集**：人工标注 8–10 个真实仓库的语言、框架、状态与关键改动
- **指标**：技术栈识别准确率、跨项目检索 Recall@5、报告事实幻觉率、
  工具调用成功率、端到端 Pass@1
- **回归**：每次改动提示词或工具定义后跑一遍，与上次结果对比，指标回退即不通过

其中**事实幻觉率**是本项目最在意的指标：口径为
「无证据支撑的陈述数 / 报告总陈述数」，逐条核对证据路径是否真实存在。
报告中不允许出现无法溯源的技术细节。

> 所有基线数字以实际运行为准，不做预估。

|---|---|
| 内核 | Python（GitPython / tree-sitter） |

## 目录结构

```
core/collector/   段 1 采集
core/parser/      段 2 解析
core/scorer/      段 3 评分
core/store/       段 4 画像存储
core/api/         能力服务（FastAPI）
plugin/           dsh 插件（TypeScript 薄层）
eval/             标注集与回归脚本
data/             项目画像（本地生成，不入库）
```

`data/` 下的画像含本机绝对路径，属隐私数据，已在 `.gitignore` 中排除，
按 README 描述重新扫描即可生成。

## 规划

| 阶段 | 内容 | 验收 |
|---|---|---|
| M0 | 环境打通 | dsh 可运行，hello 插件挂载成功，模型调用鉴权通过 |
| M1 | 采集 / 解析 / 评分 | 3 个仓库跑通，技术栈标签带证据位置 |
| M2 | 服务化 + 工具注册 | 在 dsh 中用自然语言查询项目 |
| M3 | 画像存储 + 报告产出 | 一次指令产出带证据的报告 |
| M4 | 评估与回归 | 五项指标有真实基线 |
